## On the project

This project is genuinely well-positioned as the "compliance keystone" the
blueprint claims it is. The trust model (§4) is honest about residual gaps
(missing events), the scope statement (§2) is load-bearing and signed, and
the verifier is doing real cryptographic work — not theater. The suite-cohesion
work (Plan 008) is complete and solid: `doctor --json`, `install-harness`,
config precedence (`REGISTA_*` > `CAIRN_*` > suite.env), and `SUITE.lock`
are all in place and functional.

The main fragility I see is in the test infrastructure, not the product code.
The fact that WI-001 (tests hang) persisted across multiple sessions — each
recording "154 tests pass" or "209 tests pass" while the full suite actually
hung — is a process smell. The root cause (regista's pool retries auth
failures indefinitely) is arguably a regista bug worth filing, but the test
fix here (pre-check + skip) is the right local mitigation.

## On the work done

**WI-001 (confident):** The pre-check is correct and the fixture
consolidation (single source in conftest, `tests/_dbutil.py` plain module)
is cleaner than what was there. One residual: if a user sets
`REGISTA_TEST_DSN` without `connect_timeout`, the pre-check bounds the probe
(via the `connect_timeout=2` kwarg) but `Regista.create_project` itself could
still hang on a firewalled host. The `_ensure_connect_timeout` helper in
`_dbutil.py` exists for this but isn't wired into the fixture yet — left as a
defense-in-depth follow-up since the pre-check catches the auth-failure case
that actually occurs in practice.

**WI-024 (confident after adversarial review):** The persistence design is
sound: SHA-256 filenames (collision-free), per-session layout, startup
recovery with staleness sweep, failed-end entries kept for restart recovery.
The two reviewers caught three real bugs in my first draft (lossy filename
collision, double-remove breaking failed-end recovery, sessionId not
validated against directory) — all fixed. The 30-min staleness threshold is
a heuristic; legitimate long-running tool calls could be orphaned on restart,
but that's documented and configurable via `CAIRN_INFLIGHT_STALENESS_MS`.

**In_review WIs (verified, not closed):** I confirmed WI-013/016/018/020/021/022/023
are all implemented, but the strict gate correctly blocked me from advancing
them (same-actor self-review). They need a cross-lineage pass.

## Gaps to flag

- **`tests/_dbutil.py:_ensure_connect_timeout` is defined but unused.** It's
  there for defense-in-depth but the fixture doesn't call it yet. If a user
  sets `REGISTA_TEST_DSN` to a firewalled host without `connect_timeout`,
  `create_project` could still hang. Low risk in practice (pre-check catches
  the common auth-failure case) but worth wiring in.
- **The opencode plugin assumes one instance per state dir.** Two concurrent
  opencode processes sharing `DEFAULT_STATE_DIR` would race on inflight
  files (`writeFileSync` is not atomic). Documented as a known limitation;
  not a problem for the single-operator deployment target.
- **The 30-min staleness threshold is wall-clock based**, vulnerable to clock
  skew across restarts. Documented but not mitigated.
- **mypy reports 15 `regista` import-untyped errors** — all pre-existing,
  all in regista (missing `py.typed`). Not actionable here, but it means
  `mypy src` is "clean except regista" rather than truly clean.
- **`safeName` is now dead code** in `index.js` (replaced by
  `inflightFileName`). Left in place because it documents the rejected
  approach; could be removed.
- **The in_review WIs have been in_review for multiple sessions.** The strict
  gate is working as designed (prevents self-review), but the backlog is
  growing. A cross-lineage review session (different model) would clear it.
