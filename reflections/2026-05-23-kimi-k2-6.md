# Session Reflection — 2026-05-23

**Work summary:** Bootstrapped the cairn v1 skeleton: wrote `pyproject.toml`, canonical event schema (`schema.py`), harness adapter (`adapter.py`) that maps Claude Code / OpenCode tool calls to substrate events, offline verifier (`verifier.py`) that replays and HMAC-verifies those events, CLI (`_cli.py`) with `verify` and `export` commands, substrate workflow YAML, and 9 passing pytest-driven unit tests. Ruff clean.

---

## On the project

This project is smartly scoped. Honest scope statement in README §2 (audit layer only, not enforcement) is the right call — many tools promise "tamper-proof AI governance" and fail because they can't actually prevent circumvention. Naming the gap explicitly gives the design intellectual honesty.

The substrate dependency is the right call too. Re-using an existing append-only signed event log means the team isn't re-inventing the verifiability primitives. The adapter pattern is elegant: substrate doesn't know about agent harnesses, and harnesses don't know about substrate.

What feels slightly fragile: the workflow state machine (`cairn_agent_actions.yaml`) is hardcoded. If every tool call creates a work item and transitions it `new → running → completed`, the system will create one work item per tool call. For a busy agent session that's thousands of work items and events — which is fine for correctness, but projection performance and audit-export size are unknown. Not a v1 concern, but something to instrument during dogfooding.

## On the work done

The adapter implementation went smoothly once the substrate event vs transition distinction clicked (`append_event` blocks workflow transitions; `transition()` is the correct API). The one failing test (`test_begin_and_end_tool_call`) caught this exact mistake — a good signal that the tests are actually exercising substrate contract, not just mocking around it.

I'm less confident in the CLI code (`src/cairn/_cli.py`). It's the only code path not tested in the pytest suite, and substrate connection handling (DSN, key path, workflow registration) is easy to get wrong in a CLI context. I would not trust `cairn export` without a manual smoke-test against a real Postgres.

The verifier is the strongest piece — it's isolated, deterministic, and the test coverage is good (signature ok, bad key, bundle file, report formatting). The file-provenance re-derivation logic is correct but depends on the auditor having filesystem access to the same paths recorded in the event payload. If a deployment moves files, the "MISSING" / "MODIFIED" output is accurate but could confuse a non-technical auditor — documentation gap.

## On what remains

Shippable order:

1. **Scope attestation as signed first-class event** — README §2 calls this non-negotiable. It's not code yet; it's a substrate event payload that says "this instance captures harnesses A, B, C." Must happen before anyone deploys this for real.
2. **Harness hook integration** — the adapter API exists but nothing intercepts actual tool calls. For OpenCode this means a skill that wraps tools. For Claude Code it means `PreToolUse` / `PostToolUse` hooks. The substrate side needs a long-lived work-item session to correlate multiple tool calls per agent turn.
3. **CI pipeline** — the tests need Postgres. A `docker-compose.test.yml` and GitHub Actions workflow (copy substrate's pattern) is straightforward.
4. **Key management for auditor bundles** — the verifier needs key material. In v1 the auditor holds the same HMAC secret as the operator, which contradicts the "external verifiability" goal. BC-196 (asymmetric signing in substrate) unblocks this.
5. **Export CLI smoke test** — verify `cairn export` actually produces a readable bundle.

Nice to have but not blocking:
- TSA timestamp anchoring (v2, RFC 3161)
- Web report (v2, not CLI)
- SDK wrapper (v1.5)

## Gaps to flag

- **`src/cairn/_cli.py`** — untested. No unit test covers CLI argument parsing, bundle loading, or export flow.
- **`src/cairn/adapter.py:155-177`** — `_resolve_begin_payload` fetches the most recent `tool_call_begin` event for a work item. If multiple tool calls share a work item (e.g. a multi-step agent turn), this logic is wrong — it will resolve the *latest* begin payload, not the correct one. Needs a causal link (parent_action_event_id in payload isn't used today).
- **`src/cairn/verifier.py:185-200`** — `digest_match` uses `post_digest` if present, else `pre_digest`. If a file was *deleted* after a Write, `post_digest` is null and `pre_digest` is stale — this reports "MISSING" which is correct but silently loses the information that the file was created (not modified).
- **`AGENTS.md`** — notes "project not registered with agent-notes-mcp yet." This remains true — I attempted registration but the MCP tool rejects unknown project slugs.
- **No `.git/` directory** — this repo is not under version control yet. A commit is not possible without `git init`.
