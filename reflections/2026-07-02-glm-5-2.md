## On the work done

**Plan 008 W-1.1** was a one-line change (`attest_scope` → `attest_session` in `cairn_hook.py:239`) plus a test assertion update. The hard work was understanding *why* — BC-005 explains it: `attest_scope` creates work items with `tool_call_begin`/`tool_call_end` transitions, making scope attestations structurally indistinct from tool events. `attest_session` uses `entity_kind="session"` via `append_event`, which is structurally distinct. The opencode plugin already used `attest_session`; the Claude Code hook was the laggard. I'm confident in this change.

**Plan 027 WI-1.2** was the larger piece. I added:
- `AssuranceLevel` class with 5 levels (`NONE`, `SELF_REVIEWED`, `INDEPENDENTLY_REVIEWED`, `HUMAN_ACCEPTED`, `INDEPENDENT_AND_ACCEPTED`)
- `AssuranceEntry` frozen dataclass carrying the level plus lineage metadata
- `_compute_assurance_levels` in the verifier — a pure function of signed events
- Report sections in text, JSON, and HTML
- 12 tests covering all 5 levels, undeclared lineage, multiple work items, report inclusion, and `all_ok` non-interference

The logic mirrors regista's `derive_authors` and `_event_lineage` — same `actor_metadata["model_lineage"]` extraction, same `_NON_AUTHOR_TRANSITIONS` exclusion set, same `same_lineage` comparison. The `lineage_source` field is `"asserted"` for now (HMAC-era); when Plan 026 lands, it flips to `"verified"` with no schema migration.

I'm confident in the assurance level computation. The one thing I'd want a second pair of eyes on: the `review_transitions` set that triggers assurance computation includes `submit_for_review` and `close_from_open` alongside the verdicts. This means a work item that was submitted for review but never got an `adversarial_pass` will still get an assurance entry (level: `NONE`). That seems right — the item entered the review pipeline but didn't complete it, and the assurance level says so honestly.

## Gaps to flag

- **WI-018 filed this session**: the opencode plugin's `attest_session` call doesn't pass `harness_config_digests`, while the Claude Code hook does. Minor parity gap, low severity.
- **`actor_metadata` is not in the signed envelope**: regista's `sign_event` doesn't include `actor_metadata` in the canonical envelope, so it can be tampered with without invalidating the signature. This is a known limitation of the HMAC-era interim posture — Plan 026 (per-actor Ed25519) closes it. The assurance level computation reads `actor_metadata["model_lineage"]` as asserted (not verified) data, which is honest about this limitation.
- **Pre-existing test failures (15)**: all `ModuleNotFoundError: No module named 'nacl'` or `entity_kind='session'` not supported in the installed regista version. These are environment issues, not code defects.
- **Regista migration 38 was pending** at session start — I applied it to the `regista` database (via the regista DB user, not the agent-notes DB user). Future agents should be aware that agent-notes uses `regista_config().dsn` (connecting to the `regista` database) while the `resolve_dsn()` function returns a DSN to the `agent_notes` database. These are different databases.
- **`_make_signed_event` helper extended**: I added `actor_metadata`, `actor_kind`, and `actor_id` parameters to the test helper. Existing callers are unaffected (all new params have defaults), but future tests can now set these fields for assurance-level and separation-of-duties testing.
