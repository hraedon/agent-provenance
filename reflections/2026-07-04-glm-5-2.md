## On the project

The project is architecturally sound. The verifier is doing real cryptographic work (signature verification, hash chain walking, TSA token verification, witness coverage) and the code is well-structured with clear separation between verification logic, report types, and formatters. The trust model (layered HMAC → Ed25519 → TSA → witness) is well-thought-out and honestly documented.

The biggest structural concern remains what the previous session flagged: the verifier mixes log verification with live filesystem checks (file provenance reads from the current filesystem, not the bundle). An auditor verifying a historical bundle gets misleading "MODIFIED" results for files that legitimately changed. This should be split into LogVerifier + RuntimeAuditor.

The hook/plugin split is clean. The Claude Code hook and OpenCode plugin share the same state directory layout and degradation log format, which is good for cross-harness auditability.

## On the work done

The 5 WIs were well-scoped and the implementations were straightforward. The adversarial review was the most valuable part — it caught a critical indentation bug (the cross-bundle check was outside the for loop), a path traversal in the JS safeSessionId, a wrong home directory resolver (import.meta.dirname instead of os.homedir()), and a TOCTOU in the size limit check. Without the review, the WI-022 cross-bundle chain check would have silently done nothing because it was outside the loop.

The WI-023 fix (sequence-numbered state files with O_EXCL) is the one I'm least confident in. The FIFO matching assumes post hooks arrive in the same order as pre hooks, which is true for current Claude Code but not guaranteed. The adversarial reviewer flagged this as critical (C1). I documented the assumption but didn't add a correlation ID because Claude Code's hook protocol doesn't provide one. If Claude Code ever parallelizes tool calls, this will silently swap work item IDs. The O_EXCL fix handles concurrent pre hooks, but the FIFO ordering issue remains a design-level risk.

The WI-020 fix (using verified=None instead of verified=False for filtered TSA batches) was a subtle semantic distinction that the adversarial reviewer caught — None means "not checked" while False means "attempted and failed," and conflating them would mislead an auditor.

The sanitization scan caught a real leak: the previous session's reflection file re-published all the scrubbed identifiers (personal email, principal_id handles, internal service account names) in prose, defeating the git history scrub. The identifier gate was catching it but the reflection was committed after the gate was introduced. Fixed by rewriting the line generically.

## Gaps to flag

- **`verifier.py` cross-bundle check**: The WI-022 check uses `events[0]` and `events[-1]` assuming append order. An attacker could reorder the events array. Should sort by `global_seq` to find the true first/last events. (Adversarial review finding #5, not yet fixed.)
- **`_claude_hook.py` FIFO matching**: `_oldest_state_file` returns the oldest by sequence number, assuming post hooks arrive in order. Out-of-order completion would silently swap work item IDs. (Adversarial review C1, documented but not fixed.)
- **`verifier.py:2444`**: `diff_bundles` now routes through `_load_bundle` but raises `ValueError` on load failure instead of returning a report. This is inconsistent with `verify_bundle` which returns an error report. Should be unified.
- **`identifier-gate.py`**: Stores all scrubbed identifiers in plaintext so it can pattern-match them. Anyone reading the public repo can see exactly what was scrubbed (including the real name). Should migrate to hash-based matching.
- **`integrations/opencode/index.js`**: `resolveConfigDigest` is untested — no Bun test exercises it. The session-start event handler that calls it is also untested.
- **`verifier.py` state pollution**: `_batch_claimed_ids`, `_witness_sig_cache` accumulate across verifications if the same Verifier instance is reused. Should be cleared at the start of each verify method. (Pre-existing, flagged by adversarial review.)
