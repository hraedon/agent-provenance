## On the project

The project is more mature than its "skeleton" status line claims, but it has
a real honesty problem right now: the README pitches "signed record of what
the agents did," and Plan 009's ground truth says *nothing attests today*. The
hook reads a field the harness doesn't send; the tests encode the wrong
assumption; digest semantics are undefined under truncation. The skeleton is
built but it's a recorder that records nothing, wired to a field that doesn't
exist. That's the single most important fact about this project right now and
it shapes everything: there is no point expanding scope until 009 lands.

The "hash, don't store" stance in v1 is not laziness — it's a genuine security
property (a stolen log of hashes is useless to an attacker). The v2 expansion
the owner asked for trades that property away for content, and that trade is
load-bearing. The owner's "opt-out with warning" stance on encryption is the
right call — it keeps the honest default (encrypted) while permitting the
documented exceptions (local dev, lower-layer TDE, perf testing) without
making the off-state silent. The scope attestation recording the
content_encryption stance as a signed field is the mechanism that makes the
opt-out auditable rather than invisible.

The dossier-is-the-portal decision is the unforced correct one. Building a
new cairn-specific portal would duplicate auth, gateway, templates, and the
patina design system — exactly the divergence the suite cohesion work exists
to prevent. dossier Plan 017 already names the agent-activity window; this
session just named it as the vehicle and wired the cross-reference.

## On the work done

This is a plan, not code, so confidence is mostly about *correctness of the
design*, not *does it run*. I'm confident in:

- The dependency ordering (009 before 010; 010 Phase 2+3 together; portal
  rides on content; new-harness research is parallelizable). The sequencing
  is the part most likely to be wrong in a plan and I think this one's right.
- The scope-attestation-as-re-attestation mechanism. README §2 is signed
  *precisely* so scope can't drift in prose — using the existing
  `attest_scope`/`attest_session` to re-attest the expanded scope is the
  honest path, not a workaround.
- The encryption stance (on by default, opt-out with warning, signed in the
  attestation). Matches the owner's explicit ask.

I'm less confident in:

- **Hermes/Agy/Codex interception surfaces.** I identified what these
  harnesses *are* (web search) but did not verify their actual hook/plugin
  APIs. WI-5.1 (per-harness research design note) is the honest hedge — the
  plan says "research first" rather than guessing. But if any of the three
  has no usable interception surface, that harness's adapter is blocked, and
  the plan doesn't currently name that risk loudly enough.
- **The delegation-depth design (WI-2.3).** `on_behalf_of` structurally
  supports a chain, but I didn't verify regista validates a multi-level
  chain (vs one level). If regista only validates one level, WI-2.3 needs a
  regista-side change too, and the dependency table doesn't list it.
- **The regista Plan 030 field-level-encryption recommendation.** I
  recommended regista-native field-level encryption (regista encrypts, cairn
  decides which fields) over app-layer encryption. That's the cleaner seam,
  but it introduces a design question (how does regista know which sub-tree
  to encrypt without knowing cairn's schema?) that WI-1 doesn't fully
  resolve. The fallback (cairn encrypts at app layer if 030 isn't ready) is
  sound, but the regista-native path may turn out to be more entangled than
  the plan suggests.

  include the pre-existing 029 work in a 030 commit or vice versa.
- **dossier is ahead of origin by 1 commit** (unpushed). My 017 edit is on
  top of that. The push will include both — the next agent should verify the
  unpushed commit is expected before pushing, or push it separately first.
- **The portal's content-key authz model is undefined (WI-4.2).** The plan
  says "TBD, depends on dossier's auth/key model." This is the most likely
  place for a late-stage design surprise — decryption in the portal means
  the portal holds or resolves the content key, and that's a new trust
  boundary not present in v1. Not a blocker for the plan, but a flagged
  design hole.
- **Redaction is named as best-effort, not a guarantee** — correct stance,
  but the plan doesn't specify what a redaction policy *is* (regex list?
  function? config file?). A deployment that turns on redaction and assumes
  secrets are stripped will be wrong. The plan says "review the policy" but
  the policy format doesn't exist yet.
