## On the project

The project is well-conceived and the README is genuinely load-bearing — it's doing the work of a design doc. The substrate coupling is a double-edged sword: it gives us signed events and replay for free, but the `substrate_version` field in the workflow YAML created a real rabbit hole (0.2.0 stated vs 0.1.0 in `_integrity.py`). That mismatch blocked the plugin for ~10 minutes until I manually deleted the old workflow row from Postgres. This is the kind of sharp edge that will bite future agents.

The code quality is good — `ruff` clean, tests pass, the adapter/verifier separation is clean. The `_bridge.py` script's structlog output leaking into stdout was an obvious-in-retrospect bug that should have been caught earlier.

## On the work done

The hardest part was the OpenCode plugin ↔ Python bridge boundary. The original `Bun.$` shell-pipe approach was silently dropping env vars and corrupting stdin. Replacing it with `Bun.spawn` + explicit `stdin.write/end()` fixed both. Silencing structlog at import time so the bridge's stdout stays pure JSON was the second gotcha — `make_filtering_bound_logger` expects a standard logging level, not an integer.

The `cairn export`/`verify` control-narrative embedding (WI-5) is straightforward but important: it forces every bundle to carry the README §4.1 caveat, which is the structural defense against user over-claiming.

Confidence is high in the bridge tests and the export/verify changes. Lower confidence in the plugin under real opencode load — I've only tested it with a mock `client.app.log` in a standalone script, not inside a live opencode session.
