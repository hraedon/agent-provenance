## On the project

The project is architecturally sound — the adapter/verifier/bridge split is clean, and the trust model (layered HMAC → Ed25519 → TSA → witness federation) is well-thought-out. The README does real work as a design doc, not boilerplate. The biggest structural concern is that the verifier mixes "log verification" (signatures, hash chains, bundle integrity) with "live system checks" (file provenance reads from the current filesystem, not the bundle). An auditor verifying a historical bundle gets misleading "MODIFIED" results for files that legitimately changed after the event. This should be split or at least clearly labeled.

The codebase has a pattern of commenting why things are done (BC-xxx references, "backward-compatible" notes) which is excellent for maintainability. But some of those comments mask real issues — e.g., the witness coverage check comments say "None means not checked, backward-compatible" but the code treats None as confirmed for Ed25519 witnesses where it means "couldn't verify." The comment made the bug invisible.

## On the work done

The 4-agent parallel review approach was effective — each reviewer found issues the others missed, and together they covered the full codebase. The verifier reviewer found the most critical issues (witness coverage, key rotation, unknown_key mislabeling). The integrations reviewer found the NaN timeout and state file permission issues.

The fixes themselves were straightforward — the hardest part was the witness coverage fix (distinguishing HMAC None from Ed25519 None without changing the data model). The solution (checking the witness registration's key_scheme) is clean but requires the registrations to be present in the bundle. If they're missing, the old behavior (None counts as confirmed) is preserved as fallback.

The git history scrub was more involved than expected. The previous session's notes claimed "git history rewritten" but two commits still had the personal email as author/committer, and one commit body contained personal principal_id handles and the internal DB service account name. The filter-branch approach worked but required two passes (first pass rewrote commits, second pass was needed because the local git config was still set to the personal identity).

I'm confident in the verifier fixes (they're well-tested by the existing 221-test suite). I'm less confident in the OpenCode plugin changes — the `isEnvTruthy` function is untested (no Bun test for it), and the NaN timeout fix is correct but untested.

## On what remains

## Gaps to flag

- **`verifier.py:554-567`**: File provenance reads from the LIVE filesystem, not the bundle. An auditor verifying a historical bundle gets current file state, not event-time state. This is misleading and should be separated from log verification.
- **`verifier.py:270,290`**: No size limits on `json.loads(path.read_text())`. A malicious multi-GB bundle will OOM. (WI-021)
- **`_claude_hook.py:74-78`**: `_call_key` hashes only the tool input, not a per-invocation ID. Repeated identical tool calls collide. (WI-023)
- **`integrations/opencode/index.js:46`**: The NaN timeout fix is correct but untested — no Bun test exercises a non-numeric `CAIRN_BRIDGE_TIMEOUT_MS`.
- **`tests/conftest.py:34-43`**: All Postgres-dependent tests silently skip. The CI reports "221 passing" but the actual adapter→regista integration is unvalidated. This is the most dangerous gap — the trust-critical path is untested in CI.
- **`_config.py:137`**: The `_parse_bool` fix is correct but the function is in `_config.py` while `_claude_hook.py` has its own `_env_truthy` — duplicated logic. Should be consolidated.
- **`verifier.py:656`**: The key rotation fix marks unverified when the predecessor key is missing, but this means any key rotation event in a bundle without the full key set will fail verification. This is correct behavior but could surprise users who provide only the current key.
