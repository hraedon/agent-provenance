## On the project

This project is in a healthy skeleton-to-functional transition. The codebase is small (~2500 lines of Python), well-structured, and the README-as-design-doc approach works well — the spec is load-bearing and the code follows it rather than the other way around.

The substrate dependency is the right call. It gives signing, event sourcing, and replay verification for free. The cost is that several interesting features (asymmetric signing, delegation chain, timestamping) are blocked on substrate-level work that can't happen here. The project has correctly identified this and tracked it as breadcrumbs rather than trying to solve it locally.

The naming situation (`agent-provenance` vs `cairn`) is still unresolved. The code uses `cairn` everywhere internally but the repo/project name is `agent-provenance`. This is harmless now but will cause confusion at publish time.

## On the work done

The three breadcrumb implementations were straightforward — the codebase had clear patterns to follow. The `diff` command was the most interesting: comparing bundles by event set, file provenance, and scope attestations required understanding the data model well enough to build a meaningful diff algorithm.

The SDK wrapper (`CairnClient`) was a good addition. The bridge-as-subprocess pattern works for harness integrations but is clunky for Python consumers. The client handles connection lifecycle, lazy init, and session management cleanly. The `tool_call` context manager is the key ergonomic win.

The key rotation support was partial by design — structural verification (predecessor key matches signer) and cryptographic verification against the predecessor key material both work, but full Ed25519 is blocked on substrate. The verifier now distinguishes "rotated to new key" from "unknown key" which was the core AP-001 ask.

One thing I'm uncertain about: the `_extract_readme_sections` fix for `###` vs `##` headings. I changed it to `line.lstrip("#").startswith(" 4.2")` which works but is fragile — any heading containing " 4.2" would match. A regex or explicit `###` check would be more robust. Worth revisiting if the README structure changes.

## Gaps to flag

- `_extract_readme_sections` heading match is fragile (`src/cairn/_cli.py:42`) — `line.lstrip("#").startswith(" 4.2")` matches any heading containing " 4.2", not just §4.2.
- `CairnClient.__del__` can throw during Python shutdown (structlog import fails when `sys.meta_path` is None) — harmless but noisy. Consider wrapping in try/except.
- `ToolCallContext.end()` doesn't guard against the client being closed before the context exits. Could produce a confusing substrate error if user calls `cairn.close()` inside a `tool_call` block.
- The `KeyRotationEntry` doesn't track the full key chain graph (predecessor→successor→successor...). It just records individual rotation events. An auditor comparing events across a bundle can't easily reconstruct the chain without post-processing.
- HTML report `_esc()` doesn't handle `'` (single quotes) — fine for attribute values using double quotes but could break if the HTML template changes.
